01 / 用户与问题

去同一个地方，
先要知道它是不是真的。

第一批想服务的是近期有出行机会、对某位艺人已有兴趣的粉丝。她们常在内容平台、截图、备忘录和地图之间切换：找到一个“同款”地点以后，还要自己核对艺人关联、地址与是否可去。这个场景来自我的观察与经历；它有多常见、用户愿意为此付出多少，仍需访谈验证。

待完成的任务
在指定城市找到可信的艺人地点，选出可去之处，再交给地图出发。
优先约束
没有可靠内容与正确落点，路线和纪念功能都无法建立信任。
产品阶段
开发预览；各云候选入口尚未合成一个正式上线版本。
本人负责
需求和范围判断、内容规则、AI 协作推进与结果审阅。

02 / 产品取舍

先解决“可信地出发”，
再扩展旅程体验。

START 曾同时展开路线、社群、投稿、物料、私人 Book 与娃娃。复盘后，我把第一条验证主线收窄为“地点证据 → 选择 → 地图交接”。通用导航交给已有地图；一个地点可复用，但每位艺人的关联证据独立；公开内容先审核，私人记忆不混入公共地点库。

03 / 核心路径

一次出发，只保留三个决定。

  1. 01

    发现地点

    保留艺人、城市与类别筛选；无结果时区分“没有覆盖”和“筛选过窄”。

  2. 02

    核对并选择

    在地点页先看关联依据与实用信息，再决定收藏或加入短路线。来源缺失时明确标为待补。

  3. 03

    交给地图

    向外部地图传递明确地址与坐标；落点错误或跳转失败时，允许复制地址并返回。

04 / 竞品与差异

地图能收藏地点，
START 要回答“为什么是这里”。

现有替代

内容平台 + 地图

粉丝自己搜集截图、核对出处、拼接路线。低门槛，但步骤分散。

成熟产品

Mapstr / Wanderlog

前者提供地点收藏与共享地图，后者结合地图和行程规划；基础工具能力已有成熟选择。

START 假设

证据 + 主题出行

把艺人关联证据、可去地点与主题路线放在同一任务中，减少反复查找和核对。

这还是待验证的差异，不是已证明的竞品优势。下一轮会让同一批近期计划出行的人，用原有工具组合、Mapstr/Wanderlog 和 START 完成同一任务，记录核对步骤、错误、时间与实际选择。

05 / 内容与运营

先让一个城市，
真的有内容可用。

冷启动建议先做一个可靠内容单元：一个城市、1—2 位艺人、10—15 个公共地点和 2 条短路线；若合格来源不足，缩小范围，不填充数量。每条内容经过候选、核对、草稿、审核、发布与纠错维护。AI 可帮助从资料中提取候选，艺人关系、地址和来源由人核实。

获客内容围绕具体出行问题制作，如“演出前后可去哪里”“如何核对同款地点”，落到对应主题页。观察有真实出行意图的人能否找到可信地点并打开地图，同时记录无结果、错误落点和纠错周转；互动量与有效使用分开看。

现阶段最重要的经营约束是内容核验与更新成本。没有足够可靠的地点，就不扩大城市或做传播承诺。

06 / 验证与进度

已经有结构，
还缺一条真实完成的路径。

现有工程已把来源标题、类型与链接接入保存、投稿审核和公开读取合同；发现页也已有搜索及艺人、城市、类别筛选。这些是工程与静态检查结果。统一入口、真实可发布内容、地图真机落点及用户任务完成仍待验。

首轮计划观察 6—8 名近期有相关出行的人，重点看能否无提示找到可信地点并完成地图交接。当前成都样本只有 2 个地图候选、0 个近期可发布地点，因此先补供给与验证，不报告留存或转化优势。
